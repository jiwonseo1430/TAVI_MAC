# CLAUDE.md — Project Operating Rules

## 0. Scope
This repository is for clinical research: data curation → statistical analysis → manuscript → peer-review response.
All data in `data/` is **de-identified**. Never re-identify, never merge with external identifiers.

## 1. Data handling
- Work from `<data_dir>/derived/` (analysis-ready tables). Treat `<data_dir>/raw/` as **read-only**. (`<data_dir>` = OneDrive data folder, see §9.)
- Do not print or paste full row-level data into chat. Use `str()`, `summary()`, `dim()`, `head(n=3)`, or schema descriptions.
- Any file with patient identifiers must never enter this repository. If you encounter one, stop and tell me.
- Every derived dataset must be produced by a script in `analysis/scripts/`, never by manual editing.

## 2. Plan / Execute separation (STRICT)
This is the most important rule in this file.

**Before touching any script, figure, table, or manuscript text, you must:**
1. Write or update a plan in `plan/<task>_plan.md` using the template in `plan/_TEMPLATE.md`.
2. Stop and wait for my explicit approval ("approved" / "진행").
3. Only then modify files in `analysis/` or `manuscript/`.

Do not "plan and execute in the same turn." Do not silently expand scope beyond the approved plan.
If execution reveals the plan was wrong, **stop, report, and revise the plan** — do not improvise a fix.

## 3. Statistical conduct
- The primary analysis is whatever the approved plan says. Post-hoc analyses must be **labeled post-hoc** in output and manuscript.
- Do not drop covariates, change thresholds, or switch models to improve a p-value. If a model fails to converge or EPV is inadequate, report it.
- Fix the random seed and record R version + package versions (`sessionInfo()`) in every script's output.
- Continuous variables: state units and any rescaling explicitly in both code comments and the manuscript.
- Complete-case vs imputed analyses must use a clearly named, single dataset; never compare models fitted on different N.

## 4. Manuscript rules
- Numbers in the text must be traceable to a script output file in `analysis/output/`. Never type a number from memory.
- Terminology, thresholds, and abbreviations must be identical across abstract, body, tables, figures, and supplement.
- Prose style: concise, non-redundant, no marketing language, no hedging filler. Prefer the shorter sentence.
- Peer-review responses: every "Changes made" bullet must quote the **actual current manuscript text**, verified by reading the file — not a paraphrase of intent.

## 5. Reviewer role (see review/)
When I invoke the reviewer, adopt an adversarial stance. Do not consult the rationale in `plan/`.
Judge only what is in `manuscript/`, `analysis/output/`, and the figures — as an external reviewer would.

## 6. Version control
Commit at these boundaries, with these prefixes:
- `plan:` — plan approved
- `analysis:` — script/result change
- `ms:` — manuscript text change
- `review:` — audit findings
Never amend or force-push a commit that produced a reported number.

## 7. Language
Manuscript and code comments: English. Discussion with me: Korean or English, follow my lead.

## 8. Progress tracking
- Maintain `PROGRESS.md` at the repository root. It holds two things: (a) a
  stage-by-stage checklist, and (b) a Mermaid flowchart of the analysis flow.
- Whenever a stage is completed (plan approved, script executed, verification,
  reviewer audit, manuscript update, etc.), update **both** the checklist and the
  flowchart in `PROGRESS.md`, then commit with `review:` (or the prefix matching the
  stage, per §6).
- When a new analysis stage or script is added, add a node to the Mermaid flowchart.
- Do this **automatically on completion of each stage** — no separate request needed.

## 9. Paths, environment, and artifacts
- Code lives in this git repo (GitHub); data and outputs live on OneDrive at
  `~/OneDrive/Research/data/TAVI_MAC/` (`raw/`, `derived/`, `output/`) and are
  **never committed**.
- Scripts resolve the data directory via `analysis/scripts/00_config.R`:
  env var `TAVI_MAC_DATA` first, else `config/config.yml` (gitignored;
  template in `config/config.example.yml`). Each computer sets its own path.
- Paths *within the repo* are written relative to the project root. Never
  hardcode absolute paths (including drive letters) in scripts.
- Run scripts from the repo root (e.g. `Rscript analysis/scripts/01_x.R`).
- Install R packages to the user library, not inside the project.
- Binary outputs (tables, figures, etc.) are gitignored and regenerated by
  scripts — never committed.

## 10. Switching computers
When finishing work to continue on another computer, do the following in order:
1. Finish the in-progress task and commit all changes (confirm a clean working tree).
2. Update `PROGRESS.md` to the current state — state explicitly where to resume on the
   next computer.
3. Run `git status` to confirm no uncommitted files remain.
4. End the session with `/exit` (do NOT use Ctrl+C — it only suspends the session).
5. Confirm OneDrive sync has finished (check-mark icon) before switching computers.

When starting on a new computer, read `git log` and `PROGRESS.md` first to restore
context. Session history is stored per-computer and does not carry over; `CLAUDE.md`,
`PROGRESS.md`, and the git history are the means of context transfer.
